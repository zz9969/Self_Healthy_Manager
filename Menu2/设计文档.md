# 饮食/运动健康管理系统 — 设计文档 v4.0

---

## 一、系统概述

本系统为 C/S 架构的饮食运动健康管理平台，核心亮点为**基于中医体质辨识的智能化饮食推荐**——融合规则引擎、协同过滤与轻量 AI 打分，综合用户体质、天气、地理位置，为每顿饭生成个性化食谱并给出养生理由。

| 层级   | 技术选型                                            |
| ------ | --------------------------------------------------- |
| 客户端 | Qt Creator 4.15.0 (Community)，C++ / Qt Widgets     |
| 服务端 | C++ / Visual Studio 2019，cpp-httplib + nlohmann/json + spdlog |
| 数据库 | MySQL 8.x                                           |
| 测试   | Google Test (服务端) / Qt Test (客户端)              |

**服务端第三方依赖：**

| 库 | 用途 | 集成方式 |
|----|------|---------|
| cpp-httplib | HTTP 服务 + 路由 + 中间件 | Header-only (httplib.h) |
| nlohmann/json | JSON 序列化/反序列化 | Header-only (json.hpp) |
| spdlog | 日志框架 | Header-only (spdlog) |
| libbcrypt | 密码哈希 (bcrypt) | 编译链接 |
| OpenSSL | 随机数生成 (RAND_bytes) | 编译链接 |
| MySQL Connector/C++ | 数据库驱动 | 编译链接 |

**四层职责说明：**

| 层级         | 职责                                                                 |
| ------------ | -------------------------------------------------------------------- |
| 数据层       | MySQL 持久化存储，关联表替代逗号分隔字段，规范化设计                   |
| 特征处理层   | 将原始数据转化为推荐可用的特征向量，含缓存和降级策略                   |
| AI 融合推荐层 | 规则引擎初筛 + 协同过滤扩展 + AI 多特征加权打分 + 热量约束选择        |
| 业务展示层   | Qt GUI 通过 ApiClient 异步调用服务端 REST API，DTO 隔离 UI 与业务模型 |

**关键架构决策：**
- 推荐引擎只在服务端运行，客户端不包含任何推荐逻辑
- DTO 层隔离客户端 UI 和服务端业务模型
- 天气数据缓存 1 小时，减少 API 调用
- 数据库连接管理采用单连接 + 线程安全互斥锁（本系统为桌面应用服务端，1~5 并发足够）
- 服务端使用 cpp-httplib 提供 HTTP 服务（线程池大小=4），nlohmann/json 处理 JSON 序列化
- 天气 API 选用心知天气（免费版 400 次/天），API Key 从环境变量读取
- 认证中间件 AuthMiddleware 统一拦截需认证的请求
- 过期 Session 每 30 分钟自动清理（Scheduler 独立线程）
- 每日凌晨 2:00 自动填充饮食记录（Scheduler 独立线程）
- 密码存储使用 bcrypt（cost=12），禁止 SHA-256
- Session ID 使用 OpenSSL RAND_bytes 生成 256bit 密码学安全随机数
- 登录频率限制：同一用户名连续失败 5 次锁定 15 分钟
- 所有 DAO 层 SQL 必须使用 Prepared Statement，禁止字符串拼接
- CacheManager 使用 QReadWriteLock 保证线程安全
- 日志框架选用 spdlog，日志保留 7 天，单文件最大 10MB
- 数据库迁移使用 schema_migrations 版本管理
- 客户端 ApiClient 采用异步信号槽模式，不阻塞 UI
- 客户端服务端地址通过 client_config.json 配置，默认 localhost:8080

**降级策略：**
- 天气 API 失败 → 使用上次缓存(即使过期) → 无缓存则默认"常温"
- 城市不在映射表 → 按省份匹配 → 仍无匹配 → "通用"
- 用户无体质结果 → 引导填写问卷 → 未填写则按"平和质"处理

**天气标签映射规则（心知天气 → 中医标签）：**
```
优先级从高到低:
1. 气温 ≤ 0℃ → "严寒"
2. 气温 ≥ 35℃ → "酷暑"
3. 湿度 ≥ 80% 且 气温 > 20℃ → "潮湿"
4. 湿度 ≤ 30% 且 气温 > 15℃ → "干燥"
5. 其他 → "常温"

天气现象辅助修正:
- text 含"雪/冰雹" → 强制"严寒"
- text 含"暴雨/大雨/雷阵雨" → 强制"潮湿"
```

### 5.2 体质判定算法

```
1. 用户回答 10 道题 (8种偏颇体质各1题 + 平和质2题)
2. 每题 5 选项, 分值 1~5
3. 每种偏颇体质: 原始分 = 该题得分 (1~5)
   平和质: 原始分 = 2题得分之和 (2~10)
4. 转化分计算:
   偏颇体质: 转化分 = (原始分 - 1) / (5 - 1) × 100
   平和质:   转化分 = (原始分 - 2) / (10 - 2) × 100
5. 判定规则:
   - 平和质转化分 ≥ 70 且 其他8种体质转化分均 < 30 → 平和质
   - 平和质转化分 ≥ 70 且 其他体质有 30~49 → 平和质+偏颇倾向
   - 某偏颇体质转化分 ≥ 50 → 该体质为主体质
   - 转化分最高的偏颇体质为主体质，次高为偏颇体质
6. 结果写入: 先删旧数据再插入
   DELETE FROM tcm_questionnaire_answers WHERE user_id=?
   DELETE FROM tcm_constitution_results WHERE user_id=?
   INSERT INTO tcm_questionnaire_answers ...
   INSERT INTO tcm_constitution_results ...
7. 饮食建议从 constitution_diet_guides 参考表按体质类型查询
```

### 5.3 规则引擎四级降级

```
Level 1 (严格): 体质适配 + 天气匹配 + 地域匹配 + 季节匹配 + 餐次匹配
    ↓ 若 0 结果
Level 2 (放宽地域/季节): 体质适配 + 天气匹配 + 餐次匹配
    ↓ 若仍 0 结果
Level 3 (仅体质+餐次): 体质适配 + 餐次匹配
    ↓ 若仍 0 结果
Level 4 (兜底): nature='平' 的通用食谱 + 餐次匹配

每级降级时 matchReason 标注 "部分条件已放宽"
```

### 5.4 协同过滤三阶段策略

```
初期 (系统总评分数 < 50):
  - CollabFilter 代码存在但 CandidateSelector 跳过调用
  - w6(协同) = 0，权重重分配:
    第一阶段(4维): w1(体质)=0.35, w2(热量)=0.25, w3(天气)=0.20, w4(多样性)=0.20
  - 用户评分仍正常记录到 user_recipe_ratings

过渡阶段 (50 ≤ 总评分数 < 200):
  - 自动启用 CollabFilter
  - 使用体质相似度: 主体质相同的用户即为相似用户
  - 取相似用户评分 ≥ 4 的食谱，按平均评分降序
  - w6 = 0.05, 其余按比例调整

成熟阶段 (总评分数 ≥ 200):
  - 完整协同过滤 (余弦相似度)
  - 取 Top-10 相似用户
  - w6 = 0.10
```

### 5.5 权重增量调整

```
触发条件: 每次用户评分后增量调整
调整幅度: α = 0.01 (更小的学习率，更稳定)

流程:
1. 获取用户高分食谱(评分≥4)和低分食谱(评分≤2)列表
2. 对每道高分/低分食谱，使用 meal_plans 中保存的快照
   重建 RecommendContext，重新调用 AIScorer 的 calc* 方法
3. 计算高分组各维度平均分 highDimAvg_i
4. 计算低分组各维度平均分 lowDimAvg_i
5. Δwi = 0.01 × (highDimAvg_i - lowDimAvg_i)
6. 归一化: wi = wi + Δwi, 然后所有 wi /= Σwi
7. 限制: wi ∈ [0.03, 0.40]
8. 持久化到 user_weight_profiles 表

收敛检测: 连续 5 次调整后权重变化 < 0.01 → 停止调整
```

### 5.6 食物替换算法

```
1. 获取当前食谱的 category + nature + calories
2. 筛选条件:
   - 同 category
   - 体质适配 (recipe_constitution 匹配, is_avoid=0)
   - 不在忌用列表 (recipe_constitution is_avoid=1 不匹配)
   - 热量差 ≤ ±30%
   - 天气/地域适配
3. 对筛选结果用 AIScorer 重新打分排序
4. 返回 Top-5 替换选项
```

### 5.7 多样性评分

```
数据来源: meal_plans 表（推荐过的食谱，而非 diet_records 实际吃过的）
理由: 多样性评分的目的是避免重复推荐

查询:
SELECT DISTINCT recipe_id FROM meal_plan_items mp
JOIN meal_plans p ON mp.plan_id = p.plan_id
WHERE p.user_id = ? AND p.plan_date BETWEEN
  DATE_SUB(CURDATE(), INTERVAL 7 DAY) AND CURDATE()

评分规则:
- 近 7 天未出现 → 1.0
- 出现 1 次 → 0.5
- 出现 2+ 次 → 0.2
```

### 5.8 自动填充机制

```
触发条件: 每日凌晨 2:00 Scheduler 独立线程
扫描逻辑:
1. 查找昨日有推荐计划(meal_plans)但无对应饮食记录(diet_records)的用户
2. 将推荐计划中的食谱自动写入 diet_records:
   - input_mode = 0 (自动)
   - quantity = meal_plan_items.quantity
   - calories = meal_plan_items.calories
3. 自动填写的记录标记为"系统自动记录"
4. 用户可在客户端修改/删除自动填充的记录
5. 写入后同步更新 daily_reports.is_stale = 1
```

### 7.3 认证中间件设计

```cpp
class AuthMiddleware {
    UserService* m_userService;
public:
    struct AuthResult {
        bool authenticated;
        int userId;
        ErrorCode code;
        QString error;
    };

    AuthResult verify(const httplib::Request& req) {
        QString authHeader = req.get_header_value("Authorization");
        if (authHeader.isEmpty()) {
            return {false, 0, ErrorCode::ERR_AUTH_MISSING_TOKEN, "Missing Authorization header"};
        }
        QString token = authHeader;
        if (token.startsWith("Bearer ")) {
            token = token.mid(7);
        }
        auto result = m_userService->verifySession(token);
        if (!result.isSuccess()) {
            return {false, 0, ErrorCode::ERR_AUTH_EXPIRED_TOKEN, "Invalid or expired token"};
        }
        return {true, result.data(), ErrorCode::SUCCESS, ""};
    }
};
```

## 九、关键算法公式汇总

### 9.1 BMR 计算（Mifflin-St Jeor 公式）

```
男性: BMR = 10 × weight(kg) + 6.25 × height(cm) − 5 × age + 5
女性: BMR = 10 × weight(kg) + 6.25 × height(cm) − 5 × age − 161
```

### 9.2 每日目标热量与单顿配额

```
TDEE = BMR × 活动系数
活动系数: 久坐=1.2, 轻度=1.375, 中度=1.55, 高度=1.725, 极高=1.9

早餐配额 = TDEE × 0.30
午餐配额 = TDEE × 0.40
晚餐配额 = TDEE × 0.30
```

### 9.3 运动消耗热量

```
消耗(kcal) = MET × weight(kg) × duration(h) × intensityFactor
intensityFactor: 低=0.8, 中=1.0, 高=1.2
```

### 9.4 AI 多特征加权打分

```
第一阶段 (食谱 < 100 道): 4 维打分
totalScore = w1 × constitutionScore    (0.35)
           + w2 × calorieScore         (0.25)
           + w3 × weatherScore         (0.20)
           + w4 × diversityScore       (0.20)
其余维度得分固定 0.5，权重为 0

第二阶段 (食谱 ≥ 100 道): 8 维打分
totalScore = w1 × constitutionScore
           + w2 × weatherScore
           + w3 × regionScore
           + w4 × calorieScore
           + w5 × nutrientScore
           + w6 × collabScore
           + w7 × seasonScore
           + w8 × diversityScore

默认权重: w1=0.25, w2=0.15, w3=0.10, w4=0.15, w5=0.10, w6=0.10, w7=0.05, w8=0.10
冷启动权重: w1=0.29, w2=0.18, w3=0.10, w4=0.18, w5=0.10, w6=0.00, w7=0.05, w8=0.10
权重范围: wi ∈ [0.03, 0.40]
```

### 9.5 体质转化分计算

```
偏颇体质: 转化分 = (原始分 - 1) / (5 - 1) × 100
平和质:   转化分 = (原始分 - 2) / (10 - 2) × 100
```

### 9.6 用户相似度（余弦相似度）

```
similarity(u1, u2) = Σ(r1i × r2i) / (√Σr1i² × √Σr2i²)
```

### 9.7 权重增量调整

```
Δwi = 0.01 × (highDimAvg_i - lowDimAvg_i)
wi = wi + Δwi, 然后归一化使 Σwi = 1.0
收敛检测: 连续 5 次调整后权重变化 < 0.01 → 停止调整
维度得分获取: 使用 meal_plans 快照重建 RecommendContext，重新调用 AIScorer.calc* 方法
```

### 9.8 天气标签映射规则

```
心知天气 API 返回 → 中医天气标签:
1. 气温 ≤ 0℃ → "严寒"
2. 气温 ≥ 35℃ → "酷暑"
3. 湿度 ≥ 80% 且 气温 > 20℃ → "潮湿"
4. 湿度 ≤ 30% 且 气温 > 15℃ → "干燥"
5. 其他 → "常温"
辅助修正: text含"雪/冰雹"→严寒, text含"暴雨/大雨/雷阵雨"→潮湿
```
